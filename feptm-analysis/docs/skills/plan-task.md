# plan-task — Create SDD Technical Plan

CLI tool: `./scripts/sdd-cli.sh`
Workflow directory: `<analysis-repo>/workflows/WF-*-*/`


Reads the context from the current WF-* workflow directory. Enters plan mode to design a technical solution. On approval, persists `plan.md` and **stops for the user to review/edit**. After the user's explicit go-ahead, re-reads `plan.md` and generates `tasks.md`.

### Usage

```
/plan-task <task description>                    # auto-detect WF-* dir
/plan-task WF-2002 <task description>            # explicit WF-* dir
```

Examples:

- `/plan-task integrate email delivery for order confirmation` — plan implementation within current workflow
- `/plan-task WF-2002 add rate limiting to password reset endpoint`

### Step 0: Session tracking

Extract session ID (run ONCE at the start of this phase):

```bash
PROJ_DIR="$HOME/.claude/projects/$(pwd | tr '/' '-')"
CLAUDE_SID=$(stat --format='%W %n' "$PROJ_DIR"/*.jsonl 2>/dev/null \
  | sort -rn | head -1 | awk '{print $2}' | xargs basename 2>/dev/null)
CLAUDE_SID="${CLAUDE_SID%.jsonl}"
echo "Session: $CLAUDE_SID"
```

Include `Session: {CLAUDE_SID}` in the final chat output.

Persist to `WF-*/session.yaml` — add or update `sessions` mapping (write only the `plan` key).

### Step 1: Find WF-* directory

If first argument matches `WF-*` pattern → use as explicit reference.
Otherwise → scan for active workflow.

Run in terminal:
```
ls ../<analysis-repo>/workflows/WF-*-*/session.yaml 2>/dev/null
```

For each found session.yaml, read it and check:

- `status` is `context_ready`

Decision table:

| Found | Action |
|-------|--------|
| Exactly 1 | Use it |
| Multiple | List all, ask user to pick |
| None | Error: "No active workflow. Run /init-task first." |

### Step 2: Load context

Read from the WF-* directory:

1. `session.yaml` — FR IDs, repos, ceremony level
2. `context.md` — full SDD context document (read into conversation)

Present brief summary:
```
Workflow: WF-{ID}-{slug} ({ceremony} ceremony)
FRs: {fr_ids}
Repos: {repos}
Task: {user's task description}
```

### Step 3: Baseline audit review

Read `{wf_dir}/baseline.yaml` (generated by /init-task). Present summary:

```
Baseline ({N} repos):
  {repo1}: {X} ERR, {Y} WARN
  {repo2}: {X} ERR, {Y} WARN
```

If `baseline.yaml` does not exist, generate it:

```bash
./scripts/sdd-cli.sh verify --wf-dir {wf_dir} --phase init
```

Then read the generated file.

If any pre-existing violations found, ask user: "Pre-existing violations found. Include remediation in plan?" Options:

1. **Fix all** — add remediation tasks for all ERR + WARN
2. **Fix ERR only** — fix errors, ignore warnings
3. **Ignore** — enforce zero new violations only

Save the decision in `WF-*/session.yaml` as `baseline_policy: fix_all | fix_err | ignore`.

If user chooses "Fix all" or "Fix ERR only", the plan MUST include remediation tasks BEFORE the main implementation tasks.

### Step 4: Draft the technical plan

Draft the technical plan in conversation (do NOT call the harness `EnterPlanMode` tool — SDD persists plans directly to `WF-*/plan.md`). Base the draft on:
- The user's task description
- The full context.md content
- SDD ceremony requirements for the detected level
- Baseline audit results + user's baseline_policy decision from Step 3

Plan content MUST follow SDD plan.md template:

```markdown
# WF-{ID}: Technical Plan

Implements: {FR IDs}
AR references: {relevant AR-* IDs — e.g. AR-GRPC-001, AR-GATEWAY-001, AR-LINEAGE-001}
Context: [context.md](context.md)

## Architecture Overview

{System diagram showing affected services, gateways, databases}

## Proto Contracts

{RPC definitions, message changes — if applicable}
{File location: <backend-repo>-proto/proto/{domain}.proto}

## REST API

{Endpoints, status codes — if applicable}
{Spec file: <backend-repo>-proto/api/*.openapi.yaml}

### OpenAPI Schema Changes

{For each new/modified schema, list:}
- Schema name, fields, types
- required vs nullable — MUST match proto message optionality
- enum values — MUST cite source (proto enum / service validation / DB constraint)
  Example: `status: enum [active, disabled]` — source: `catalog_management.rs:97`
- Source proto message: `{package}.{MessageName}` from `proto/{domain}.proto`

{If no schema changes: "No schema changes."}

## Database Schema

{Migrations, table design — if applicable}
{Migration file: {service}/migration/src/m{TIMESTAMP}_{INDEX}_{name}.rs}

## Implementation Details

{Service logic, config changes, error handling}

## Security Considerations

{Auth, input validation, rate limiting — if applicable}

## Config Changes

{New config keys with defaults}
{Config prefix: <PROJECT>_{SERVICE}__}
```

### Step 5: Persist plan.md and HARD STOP for user review

After drafting in Step 4, persist the plan and stop:

1. Write `WF-*/plan.md` directly from the drafted content. Do NOT route the plan through any harness buffer (`~/.claude/plans/*.md`); `WF-*/plan.md` is the only authoritative location.

2. **HARD STOP.** Output to the user:

   > Plan written to `WF-*/plan.md`.
   > Open it in your IDE — edit anything, save the file. Your edits are the source of truth.
   > When you are done editing, reply "ok" (or any explicit go-ahead) and I will:
   > - re-read `plan.md` (your edits, not my in-memory draft)
   > - generate `WF-*/tasks.md`
   > - update `WF-*/session.yaml` (status → planned)
   > - update `WF-*/STATUS.md`
   > Until then I will not write any other file or run any command.

3. **STOP.** Do NOT proceed to Step 6 on the same turn. Wait for an explicit user signal — a chat reply confirming the plan, or invocation of `/implement-task`. If the user replies with edits or questions, address those without advancing.

**Acceptance criteria for plan.md** — verify before the hard-stop:

- [ ] `Implements:` lists all FR-* IDs from session.yaml
- [ ] `AR references:` lists relevant AR-* IDs (check context.md AR specs section)
- [ ] Each section references specific files with paths

### Step 6: After user signal — re-read plan.md, generate tasks.md, finalize

Trigger: explicit user approval after Step 5's hard stop ("ok", "proceed", "go", etc.) or invocation of `/implement-task`.

1. **Re-read `WF-*/plan.md`.** The user may have edited it since Step 5. The on-disk file is now the source of truth; do NOT regenerate from your in-memory draft.

2. Generate `WF-*/tasks.md` — break the (possibly edited) plan into ordered implementation tasks:

```markdown
# WF-{ID}: Tasks

| # | Task | Req | Depends on | Status | Completed |
|---|------|-----|------------|--------|-----------|
| T-01 | Proto: define {RPC} in proto/{domain}.proto | {FR-ID} | — | pending | |
| T-02 | DB migration: create {table} in {service}/migration/ | {FR-ID} | T-01 | pending | |
| T-03 | Service: implement {logic} in {service}/src/logic/ | {FR-ID} | T-02 | pending | |
| T-04 | gRPC handler: implement {handler} in {service}/src/grpc/server.rs | {FR-ID} | T-03 | pending | |
| T-05 | Gateway: add REST endpoint in {gateway}/src/routes/{module}.rs | {FR-ID} | T-04 | pending | |
| T-06 | OpenAPI: update spec in {name}.openapi.yaml | {FR-ID} | T-05 | pending | |
| T-07 | E2E scenario: update {scenario}.md | {FR-ID} | T-05 | pending | |
| T-08 | Traceability: add @req annotations | {FR-ID} | T-04, T-05 | pending | |
```

`Completed` column: filled by implement-task when status changes to `done` or `blocked`. Format: `YYYY-MM-DDTHH:MM`.

Task ordering follows SDD spec-first principle: proto → migration → service logic → handler → gateway → OpenAPI → tests → traceability.

**Task description MUST reference specific files.** This enables automated diff verification in implement-task and finalize-task.

Good: `Backend: add EmotionDetail mapper case in src/mappers.rs`
Bad: `Backend: add response struct`

Good: `OpenAPI spec: add x-requirement to 6 catalog operations in <project>.openapi.yaml`
Bad: `OpenAPI spec: fix x-requirement`

**MANDATORY**: The LAST task in every plan MUST be a full audit of all affected repos:

```markdown
| T-{NN} | Audit: full repo audit — zero ERR, zero WARN in touched files | {FR-ID} | T-{NN-1} | pending | |
```

This task runs `sdd-cli audit --files {all changed files}` and verifies zero violations in files touched by this workflow. WARNs in untouched files are reported but do not block.

3. Update `WF-*/session.yaml`: set `status: planned`, save `baseline_policy` (if not already recorded in Step 3).

4. Update `WF-*/STATUS.md`: add plan summary section + baseline audit results.

**Acceptance criteria for tasks.md** — verify before reporting:

- [ ] Each task description references specific files with paths
- [ ] The last task is a full repo audit (zero ERR, zero WARN in touched files)
- [ ] Tasks in tasks.md follow spec-first ordering: proto → migration → service → handler → gateway → OpenAPI → tests → traceability

### Step 7: Report and end of phase

```
Plan written: WF-*/plan.md
Tasks: {N} items in WF-*/tasks.md
Session: {CLAUDE_SID}
Next: /implement-task
```

**CRITICAL BOUNDARY:**

The user's approval at Step 5 covered the contents of `plan.md`. `tasks.md` is a deterministic derivation from that plan, so generating it here did NOT need a second gate. But before any code is touched:

1. **Do NOT edit or write** any file outside the WF-* directory in this phase.
2. **Do NOT run** build/test commands in this phase.
3. **Do NOT launch** implementation agents in this phase.
4. **Do NOT enter the harness plan mode.** SDD plans are persisted directly to `WF-*/plan.md`; the harness `EnterPlanMode` / `ExitPlanMode` flow is not used by this procedure.

Whether to continue automatically into `/implement-task` follows the chaining rule:

- **Standalone `/plan-task`** → STOP. Wait for the user to invoke `/implement-task` explicitly.
- **Chained from higher-level intent** ("implement X") → after the user approved `plan.md` at Step 5, that approval covers running `/implement-task` next on the same turn. Proceed to it.

ANY code editing is the exclusive responsibility of `/implement-task`.
